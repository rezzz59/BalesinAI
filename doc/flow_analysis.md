# Flow Analysis: How AI Responds to Various Customer Messages

## Overview

The project uses **LangGraph** to orchestrate a multi-step workflow that classifies intent → looks up catalog → composes reply → sends WhatsApp. The system handles 4 main intents and multiple fallback scenarios.

---

## 🎯 Intent Classification (via LLM)

All incoming messages pass through `classify_intent` which uses an LLM classifier with conversation history. The 4 intents are:

| Intent | Trigger Examples | Confidence Threshold | Has Complaint Signal |
|--------|-----------------|---------------------|---------------------|
| `faq` | Pertanyaan tentang harga, ongkir, stok, warna, garansi, cara order | Default: 0.7 | Detects: "kecewa", "malas", "refund", "batal", "dibayar tapi ga sampai", nada kesal |
| `check_product` | User menyebut produk spesifik: "ada ga jeans biru ukuran 30?", "Kaosnya ada?" | Default: 0.7 | Rarely flagged as complaint unless语气 negative |
| `confirm_order` | "saya pesan", "oke order", "beli 2 pcs", "mau bayar", "langsung order" | Default: 0.95 | No |
| `unclear` | "halo", "siang", "ada yang bisa dibantu?", off-topic messages | Default: 0.9 | No |

### Example Classifications:

```
User: "Harga kaosnya berapa?"
→ intent: "faq", confidence: 0.9, has_complaint_signal: false, sentiment: neutral

User: "udah 5 hari ga diterima!"
→ intent: "faq", confidence: 0.7, has_complaint_signal: true, sentiment: negative

User: "saya mau order 2 pcs"
→ intent: "confirm_order", confidence: 0.95, has_complaint_signal: false, sentiment: positive

User: "halo selamat siang"
→ intent: "unclear", confidence: 0.9, has_complaint_signal: false, sentiment: positive
```

## 🔄 Decision Flow

### Flow 1: FAQ with Good Catalog Match

```
User: "Apakah ada yang warna biru ukuran M?"
    │
    ▼ classify_intent
    ┌─────────────┐
    │ intent = faq│
    │ confidence  │
    │   ≈ 0.9     │
    └──────┬──────┘
           ▼ (should_fallback = False)
    lookup_catalog()
    ┌────────────────────┐
    │ cari di FAQ Sheets│
    │ match found!       │
    └──────┬─────────────┘
           ▼ route_after_lookup()
    compose_reply() ──► LLM.compose_reply_with_history()
    │                     │
    │ (retrieved_row = {"pertanyaan":"...", "jawaban":"..."})
    ▼                     ▼
validate_reply(strict) ✓ (facts from source row only)
    │
    ▼ send_whatsapp("Reply langsung dari catalog")
    │
    ▼ write_chat_log
    END
```

**Balasan:** Response generated by LLM based strictly on FAQ catalog answer (with warm polite tone). If match_kind is "high/medium", LLM can acknowledge user's attribute (color/size) mentioned in message.

### Flow 3: Confirm Order (Special Fast Path)

```
User: "Saya mau order 2 pcs kaos hitam"
    │
    ▼ classify_intent
    intent = confirm_order (auto-high confidence)
    │
    ▼ (should_fallback = False)
lookup_catalog() → {} (no FAQ/product match for order confirmation)
   │
   ▼ route_after_lookup() → compose_reply (NOT fallback!)
   │
   ┌──────────────────────────────────────┐
   │ SHORT-CIRCUIT in compose_reply():   │
   │ intent == "confirm_order" → NO LLM │
   │ Reply template hardcoded:          │
   │ "Terima kasih ordernya! Owner     │
   │ akan follow up untuk konfirmasi    │
   │ pembayaran ya 🙏"                    │
   └────────────────────────────────────┘
   │
   ▼ action = "order"
send_whatsapp()
│
▼ write_chat_log
END
```

**Key:** Order confirmation skips LLM entirely — instant response.

### Flow 4: No FAQ Match Found (Low/None Overlap Score)

```
User: "Garansi berapa bulan?"
    │
    ▼ classify_intent → intent = faq, confidence ≈ 0.9
    ��
    ▼ lookup_catalog()
    ┌─────────────────────┐
    │ FAQ tidak ditemukan│
    │ atau overlap score │
    │ < 0.5              │
    └────────┬────────────┘
             ▼ route_after_lookup()
    compose_reply_fallback() ←──┐
             │                │ (NO LLM call!)
             ▼                │
{ reply_text: "Sedang kami cek, owner akan follow up ya 🙏",
  action: "fallback",
  fallback_reason: "no_faq_match" }
             │
    send_whatsapp? ───► fallback_human() (because action=fallback)
            │           │
            ▼           ▼
    Owner receives     Send to buyer:
    full message + intent/confidence/sentiment/reason
    "Sedang kami cek, owner akan follow up ya 🙏"
            │
    write_chat_log
    END
```

**Critical:** When FAQ lookup returns nothing or match is too weak, system **automatically escalates to human handoff**. This is safe because we don't want LLM making things up.

### Flow 6: Complaint Signal Detected

```
User: "Barusan bayar, tqtp 3 hr bla bla, udh ga ketololsaaan!"
    │
    ▼ classify_intent → intent = check_product (or whatever) but
      has_complaint_signal = TRUE, sentiment = negative
    │
    ▼ should_fallback() = True (complaint_signal overrides everything)
    ┌────────────────────┐
    │ fallback_human()   │ ← priority #1 in fallback_reason_for()
    └────────┬───────────┘
             ▼
    Owner gets: [FALLBACK] [urgency flag], full message with complaint details
    Buyer gets automatic ack: "Sedang kami cek..."
             │
    write_chat_log
    END
```

Complaints get immediate escalation regardless of intent.

---

### Flow 7: LLM Validation Fails (Retries & Fallback)

```
compose_reply() → llm_client.compose_reply_with_history()
    │
    ├── Attempt 1: reply generated
    │        ├── validate_reply() ✗ (hallucination detected)
    │        │   ┌─────────────────────────────────┐
    │        │   │ Log warning → retry with strict hint│
    │        │   └─────────────────────────────────┘
    │        │
    │        ├── Attempt 2: reply with strict hint appended
    │        │   ├── validate_reply() ✗ (still hallucinating)
    │        │   │   ┌─────────────────────────────────┐
    │        │   │   │ Log warning → VERBATIM FALLBACK  │
    │        │   │   └─────────────────────────────────┘
    │        │   │
    │        │   ▼ _verbatim_fallback(state)
    │        │   { reply_text: catalog_answer wrapped OR product detail + ready status,
    │        │     action: "reply" }
    │        │
    │        ▼ send_whatsapp(verbatims)
    │
    ��── If LLMError occurs at any point → _verbatim_fallback immediately
```

The system gives the LLM **two chances** to produce a valid reply. On second failure, it falls back to verbatim text from the source row — no invented facts.

---

### Flow 8: All Backends Fail (Multi-LLM Fallback)

With `FallingBackLLMClient` configured with priority chain like `["adacode", "gemini"]`:

```
classify_intent() → AdaCodeLLMClient
    │
    ├── Succeeds → proceed normally
    │
    ├── Fails (LLMError: network/auth/API issue) → next in chain
    │        ▼ GeminiLLMClient
    │           ├── Succeeds → proceed normally
    │           └── Fails → raise last LLMError → FallingBackLLMClient propagates error
    │                              └── Caught by caller (e.g., route_after_classify) 
    │                                    → likely triggers fallback due to error
    │
    compose_reply() → Same fallback chain across all 4 methods
```

This ensures resilience if one LLM provider goes down.

|------------------|--------|---------------|--------------|------------|-------------------|

## 🔍 Key Observations

1. **Fail-safe design**: Any ambiguity (low confidence, no match, complaints, unclear intent) routes to human — never risks hallucination.

2. **Fast path for orders**: Confirm order bypasses LLM entirely with a hardcoded template — instant and reliable.

3. **Two-stage LLM resilience**: First tries clean composition, then retries with strict constraint reminder, finally falls back to verbatim text if both fail.

4. **Multi-LLM failover**: With `FallingBackLLMClient`, if Adacode fails (503/auth/token expiry), system automatically switches to Gemini without user noticing.

5. **Human-in-the-loop escalation**: Every fallback sends owner the full context (message, intent, confidence, sentiment, reason) via WhatsApp plus automated buyer acknowledgment.

6. **Conversation memory**: All nodes use `state["messages"]` list for multi-turn context so follow-up questions are handled correctly.

7. **Audit trail**: Every chat writes to SQLite (`write_chat_log`) with intent, confidence, response, and fallback reason for later analysis.

8. **Strict fact verification**: `validate_reply()` checks that numeric facts (price, size, stock indicator) appear EXACTLY as in source row — prevents price/format hallucinations.
